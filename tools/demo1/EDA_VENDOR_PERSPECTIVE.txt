1. SYNTHESIS DEBUGGING (Genus RTL Compiler Perspective)
═══════════════════════════════════════════════════════════════════════════

🔧 PROBLEM: Post-synthesis netlist has timing violations or functional bugs

Your Tool's Role:
─────────────────────────────────────────────────────────────────────────

✓ CONE OF INFLUENCE ANALYSIS
  Genus Equivalent: "report_timing -from [pin] -to [pin]"
  
  What Genus Does:
    - Shows timing paths between registers
    - Reports critical path delays
    - But hard to visualize gate-level connectivity
  
  What Your Tool Adds:
    • backward_cone("output_reg") → See ALL contributing logic
    • forward_cone("modified_gate") → Impact analysis after ECO
    • Visual HTML graph → Share with team, easier to debug
    • No need to know exact pin names
  
  Use Case:
    After synthesis, timing fails on path A→B
    → backward_cone("reg_B") shows 500 gates in the path
    → Identify which combinational logic is too deep
    → Guide restructuring/retiming decisions

✓ CRITICAL PATH ANALYSIS
  Genus Equivalent: "report_timing -max_paths 10"
  
  What Genus Shows:
    - Longest timing paths with delays
    - But only between flip-flops
  
  What Your Tool Adds:
    • find_critical_paths() → Pure logic depth (gate count)
    • Shows combinational complexity regardless of delay
    • Helps identify areas needing pipeline registers
  
  Use Case:
    Path has 50 gates but meets timing (fast gates)
    Path has 10 gates but fails timing (slow gates)
    → Your tool finds both, Genus optimizes the slow one

✓ LOOP DETECTION
  Genus Equivalent: Synthesis fails with "combinational loop" error
  
  What Genus Does:
    - Aborts synthesis
    - Points to one loop in RTL
  
  What Your Tool Adds:
    • detect_combinational_loops() → Find ALL loops at gate level
    • Distinguish between sequential (OK) and combinational (BAD)
    • Shows the exact gate instances forming the loop
    • Debug post-synthesis when Genus netlist has issues
  
  Use Case:
    Synthesis creates unintended latch due to incomplete if-else
    → Your tool pinpoints exact gates in the loop
    → Engineer fixes RTL, re-synthesizes

2. FORMAL VERIFICATION (Conformal LEC Perspective)
═══════════════════════════════════════════════════════════════════════════

🔧 PROBLEM: Conformal shows non-equivalent points after ECO or optimization

Your Tool's Role:
─────────────────────────────────────────────────────────────────────────

✓ ECO IMPACT ANALYSIS
  Conformal Equivalent: "diagnose" command on failing compare points
  
  What Conformal Does:
    - Reports which outputs are non-equivalent
    - Shows cone of logic for failing points
    - But limited to RTL vs. Netlist comparison
  
  What Your Tool Adds:
    • Compare two gate-level netlists (pre/post ECO)
    • forward_cone("modified_gate") → See ECO impact radius
    • backward_cone("failing_output") → Root cause analysis
    • Visualize to explain to design team
  
  Use Case:
    Engineer makes manual ECO in netlist
    → Conformal fails on 5 outputs
    → backward_cone() on each output shows common gate
    → Fix the root cause, not symptoms

✓ DEBUG NON-EQUIVALENCE
  Conformal Equivalent: "add compare point", "set mapping"
  
  What Conformal Shows:
    - Boolean mismatch between designs
    - Hard to understand structural differences
  
  What Your Tool Adds:
    • trace_signal_path() → See structural connectivity
    • verify_gate() → Check if connections changed
    • Export cone for visual diff review
  
  Use Case:
    After clock gating insertion:
    → Conformal reports non-equivalence
    → Your tool shows ICG (Integrated Clock Gate) inserted
    → backward_cone() confirms only clock changed, data path OK
    → Set equivalent points in Conformal appropriately

3. PHYSICAL DESIGN (Innovus Implementation Perspective)
═══════════════════════════════════════════════════════════════════════════

🔧 PROBLEM: Timing closure, congestion, power optimization

Your Tool's Role:
─────────────────────────────────────────────────────────────────────────

✓ CONGESTION ANALYSIS
  Innovus Equivalent: "check_place -congestion"
  
  What Innovus Shows:
    - Physical congestion hotspots
    - Route overflow regions
  
  What Your Tool Adds:
    • Logical fanout analysis (stats command)
    • High fanout nets (>50) likely to cause congestion
    • backward_cone() on congested regions
    • Suggest buffer insertion points
  
  Use Case:
    Innovus shows congestion in region X
    → Your tool: gate g17194 has 75 fanout
    → Add buffer tree in synthesis
    → Re-place and congestion reduced

✓ TIMING CLOSURE ECO
  Innovus Equivalent: "eco_netlist" for timing fixes
  
  What Innovus Does:
    - Adds buffers, resizes gates
    - Hard to predict side effects
  
  What Your Tool Adds:
    • Before ECO: forward_cone("slow_gate") → impact
    • After ECO: backward_cone("affected_path") → verify
    • Export both cones, compare visually
  
  Use Case:
    Innovus upsizes gate to fix timing
    → forward_cone() shows 20 gates affected
    → Check if power budget exceeded
    → Verify no new violations on downstream paths

✓ CLOCK TREE ANALYSIS
  Innovus Equivalent: "report_clock_tree"
  
  What Innovus Shows:
    - Clock tree structure
    - Skew, insertion delay
  
  What Your Tool Adds:
    • trace_signal_path("clk", "reg") → See clock path gates
    • Identify clock domain crossings
    • Find registers on same clock (for pipelining)
  
  Use Case:
    Clock skew violation between reg_A and reg_B
    → trace_signal_path() shows different clock buffers
    → Balance clock tree in Innovus CTS

4. FUNCTIONAL DEBUG (Simulation/Emulation Perspective)
═══════════════════════════════════════════════════════════════════════════

🔧 PROBLEM: Post-synthesis/post-layout simulation fails

Your Tool's Role:
─────────────────────────────────────────────────────────────────────────

✓ BUG LOCALIZATION
  Traditional Debug: Waveform analysis (VCD viewer)
  
  What Simulation Shows:
    - Signal values over time
    - Where the bug manifests
  
  What Your Tool Adds:
    • backward_cone("wrong_signal") → Suspect gates list
    • Reduce from 3000 gates to 50 suspect gates
    • Add assertions/breakpoints only on suspect gates
    • Faster re-simulation
  
  Use Case:
    Output bit[7] wrong at cycle 1000
    → backward_cone("output[7]") → 80 gates
    → VCD trace only those 80 signals
    → Find which gate has wrong input
    → Trace backwards iteratively

✓ TESTBENCH CREATION
  Traditional: Manually identify signals to monitor
  
  What Your Tool Adds:
    • forward_cone("interface_reg") → All affected outputs
    • Automatically generate monitor list
    • Export to SystemVerilog assertion code
  
  Use Case:
    Verifying new feature in block X
    → forward_cone("feature_enable") → 200 gates
    → Generate checkers for all 200 gates
    → Comprehensive coverage

✓ GATE-LEVEL SIMULATION OPTIMIZATION
  Problem: Gate-level sim is 100x slower than RTL
  
  What Your Tool Adds:
    • Identify critical cones for targeted simulation
    • backward_cone("critical_output") → Simulate only this
    • Rest of design: Use behavioral models
    • 10-50x speedup
  
  Use Case:
    Full-chip gate-level sim takes 1 week
    → Identify 5 critical outputs
    → Simulate only their cones (500 gates each)
    → Complete in 1 day, find bugs faster

🔧 PROBLEM: High power consumption, leakage, hot spots

Your Tool's Role:
─────────────────────────────────────────────────────────────────────────

✓ POWER HOTSPOT ANALYSIS
  Voltus Equivalent: "report_power -by_hierarchy"
  
  What Voltus Shows:
    - Power by module
    - Switching activity
  
  What Your Tool Adds:
    • High fanout → High capacitive load → High power
    • stats command → Find gates with >50 fanout
    • forward_cone() → Estimate switching activity propagation
  
  Use Case:
    Power report shows block_A uses 40% power
    → Your tool: 3 gates in block_A have >100 fanout each
    → Add clock gating on those gates
    → Re-analyze: 20% power reduction

✓ CLOCK GATING OPPORTUNITIES
  Traditional: Manual inspection of RTL
  
  What Your Tool Adds:
    • Find all registers (SDFF*, DFF* gates)
    • backward_cone() on each → Find enable logic
    • Identify groups with same enable
    • Suggest ICG insertion points
  
  Use Case:
    Design has 500 registers, no clock gating
    → Your tool groups 200 regs with same enable
    → Add 1 ICG → 40% clock power saved

       ↓

       ↓

       ↓
  [Voltus] Power Analysis
       ↓
  [Tapeout]


WHERE YOUR TOOL FITS:
─────────────────────────────────────────────────────────────────────────

  1. POST-SYNTHESIS DEBUG (After Genus)
     ├─ detect_combinational_loops() → Fix before P&R
     ├─ find_critical_paths() → Guide floorplanning
     └─ Stats → Verify gate count matches spec

  2. ECO VERIFICATION (With Conformal)
     ├─ backward_cone() → Debug LEC failures
     ├─ forward_cone() → Assess ECO impact

     ├─ trace_signal_path() → Understand failing paths

  4. SIGN-OFF CHECKS (Before Tapeout)
     ├─ detect_loops() → Final sanity check
     ├─ Compare pre/post-layout netlists
     └─ Verify ECOs didn't break connectivity

  5. POST-SILICON DEBUG (After Fab)
     ├─ backward_cone() → Localize failing test vectors
     ├─ Export cones → Guide probe point selection
     └─ Root cause → Guide metal mask ECO

───────────────────────────────────────────────────────────────────────────

  ✓ Gate-level visualization (Conformal is abstract)
  ✓ Cone export for collaboration
  ✓ No licensing constraints

───────────────────────────────────────────────────────────────────────────
  ✓ Static analysis (no simulation needed)
  ✓ Structural connectivity (waveforms show behavior)
  ✓ Exhaustive (all paths, not just exercised ones)
  ✓ Faster (seconds vs. hours of simulation)

9. REAL-WORLD SCENARIOS
═══════════════════════════════════════════════════════════════════════════

SCENARIO A: TIMING ECO IN INNOVUS
───────────────────────────────────────────────────────────────────────────
  Problem: Critical path fails timing by 50ps
  
  Commercial Flow:
    1. Innovus: report_timing → See failing path
    2. Innovus: eco_netlist → Auto-fix (adds buffers)
    3. Hope it works, re-run STA
  
  With Your Tool:
    1. backward_cone("endpoint") → 200 gates in path
    2. Export cone, identify bottleneck (6-input NAND)
    3. Suggest replacing with 2x 3-input NANDs in synthesis
    4. Or: Add pipeline register (break into 2 stages)
    5. Targeted fix, not blind ECO

SCENARIO B: CONFORMAL LEC FAILURE
───────────────────────────────────────────────────────────────────────────
  Problem: 50 outputs non-equivalent after clock gating
  
  Commercial Flow:
    1. Conformal: diagnose → Shows logic mismatch
    2. Manual inspection of RTL vs. netlist
    3. Hours of debugging
  
  With Your Tool:
    1. Compare both netlists (before/after CG)
    2. backward_cone() on failing outputs
    3. Find common ICG (clock gate)
    4. Realize: ICG enable logic wrong
    5. Fix enable, re-verify → Pass in minutes

SCENARIO C: POST-SILICON BUG
───────────────────────────────────────────────────────────────────────────
  Problem: Chip fails functional test, expensive debug
  
  Commercial Flow:
    1. ATE logs show output bit[5] fails
    2. Engineers guess root cause
    3. Order new chip with fixes ($$$, months delay)
  
  With Your Tool:
    1. backward_cone("output[5]") → 80 suspect gates
    2. Physical layout: All 80 gates in region X
    3. Probe region X on chip → Isolate to gate g1234
    4. Root cause: Metal short in g1234
    5. Metal-only ECO fix → $$ saved, weeks faster
